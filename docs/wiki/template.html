Writing code mods for Bellwood

Bellwood mods are C source files packed into an .o2r archive. The game compiles them with TinyCC when it loads them, so a mod is plain text you can read, and the same archive works on every platform that runs code mods. This wiki covers how to build one and every function, structure and event a mod can use.

Guide

Your first mod

Start from workspace/template, inside a Bellwood checkout or the mod SDK zip. The SDK has the same layout and holds only what mods are built against: the headers, the mod tools, the template and the custom-content example. A Bellwood checkout writes it with cmake --build build --target mod_sdk.

  1. Copy the template

    Copy workspace/template to workspace/my-mod and change project() in its CMakeLists.txt; the archive is named after it. Fill in manifest.json.

  2. Write the entry points 
    #include "mod.h"
#include "port/events/Events.h"
#include <stdio.h>

static void OnMoneyChanged(IEvent* event) {
    PlayerMoneyChanged* money = (PlayerMoneyChanged*)event;
    printf("Wallet: %u -> %u Bells\n", money->prev, money->now);
}

MOD_INIT() {
    REGISTER_LISTENER(PlayerMoneyChanged, EVENT_PRIORITY_NORMAL, OnMoneyChanged);
}

MOD_EXIT() {
}
  3. Build the archive
    cmake -B build -S .
cmake --build build --target package_mod

    You need CMake 3.10 or newer and Python 3. Pillow is only needed for .png and .gltf files used with #asset.

  4. Install it

    Copy the .o2r into Bellwood's mods/ folder and start the game. Compiler errors appear under Mods › Installed. Reload Scripts in the same menu rebuilds every mod without restarting.

How the build packages a mod

The build merges each .c file in src/ with every Bellwood and libultraship header it includes into one self-contained file under output/dist/, and lists those files in build.gen. The game compiles exactly those files, so a mod never depends on headers being present on the player's machine. Everything from one source file ends up in one translation unit: mark helpers static so they don't collide with the game or other mods.

mod.h defines MOD_INIT and MOD_EXIT, routes malloc and free through the engine's allocator, and provides CALL_FUNC for calling into another mod.

Guide

Loading, reloading and cleanup

At startup the game mounts every enabled mod archive, compiles each mod's sources, then calls ModInit in dependency order. When a mod unloads, on exit or on Reload Scripts, the game calls its ModExit and then releases everything the mod registered:

  • content from the port/api headers: actors, furniture, items, villagers, sounds, messages and the rest;
  • event listeners, Mods menu pages and widgets, and GUI draw callbacks;
  • anything registered from the mod's actor and furniture callbacks.

So MOD_EXIT is optional. Use it only to undo what the mod set up some other way, such as a game variable it changed directly. The C_Unregister* functions are for taking content away while the mod keeps running. Furniture placed in the room on screen is destroyed with the old code and constructed again with the new code when the mod reloads.

The Mods menu

Mods › Installed lists every archive with a manifest and its state: loaded, failed to build (with the compiler's message), skipped (with the reason) or disabled. Each mod has an Enabled switch and a Priority. Mods with a higher priority are mounted later, so their files replace those of mods before them, and their code initializes later; dependencies always initialize first. Both settings take effect on the next start. A disabled mod isn't mounted at all.

Dependencies

A version range is a list of comparisons separated by spaces or commas: >=, >, <=, < and =. A version without an operator is a minimum. A mod whose dependency is missing, failed to build or falls outside the range is skipped with a notification, along with every mod that depends on it. Call into a dependency with CALL_FUNC(mod, func, ...) from mod.h.

Definition structs only grow at the end. Each C_Register* macro passes sizeof the definition the mod was built with to the *Sized function behind it, so fields added in later versions read as zero for older mods. Always call the macro, not the *Sized function. port/api/player.h and port/api/town.h keep their signatures across versions; the game's own functions may not.

Content ids and saves

Every piece of content has an id string such as "mymod.gem". The game gives it an item number when it is registered, from the ranges below. Each town file records the numbers of the ids it uses. When a town loads with different numbers, because mods were added, removed or loaded in another order, or because it was saved on another computer, its content is renumbered to match. A town that uses content from mods that aren't loaded shows a notification naming them, and that content shows as unknown until the mods are back.

Keep ids stable. Never reuse an id for different content, and never change the id of content players may already own. Don't store raw item numbers in your own save data either: store the id and look the number up again.

Values a mod keeps for a town go through savedata.h, which stores them in the town's save file. Settings that belong to the player rather than the town go through cvar.h.

Assets: textures and models

C_ASSET(name, path) declares one of the game's own assets by its path in the game archive, to use as a Gfx*, texture or palette. The paths match the *_PATH macros in the game's include/assets headers.

C_ASSET(sPodiumModel, "data/model/obj_e_ghog/obj_e_ghog_model");

#asset converts a file next to the source into the game's formats when the mod is built, and places the bytes inside an array:

static const u8 sIcon[] = { #asset "textures/icon.png" CI4 };
static const u8 sIconPalette[] = { #asset "textures/icon.png" CI4_PAL };
static const u8 sBoltModel[] = { #asset "models/bolt.gltf" NPC_MODEL };
FormatSourceUse
(none), RGBA32PNGFull colour, decoded when the game loads it.
RGBA16PNG5 bits per channel and 1 bit of alpha.
CI4, CI8PNG16 or 256 colours from a palette. Item icons, carpets, wallpapers and shirts are CI4.
CI4_PAL, CI8_PALPNGThe palette for the same PNG's CI4 or CI8 texture.
I4, I8, IA4, IA8, IA16PNGGreyscale, with or without alpha.
MODEL, MODEL_XLUglTFA structure's display list, opaque or translucent part.
ROOM_MODEL, ROOM_MODEL_XLUglTFA structure room's walls and floor.
NPC_MODEL, NPC_ANIMglTFA villager model on the 26-joint villager rig, or its first animation.

For CI formats, a PNG that already has a palette of up to 16 or 256 colours keeps its colours in order; any other PNG is reduced, with transparent pixels on colour 0. Colours are stored with 5 bits per channel, so they can shift slightly. In models, a tile is 40 units across, y is up and z points south towards the camera; each material becomes a CI4 texture of up to 64×64 texels. workspace/custom-content/README.md has the full rules for structure, room and villager models.

Guide

Text and messages

Every string a mod passes is UTF-8. Names are cut to the length the game shows: 16 characters for item names, 8 for villager and structure names. Message text uses \n for a new line, and the game's control codes as tags, the same ones tools/msg_tool.py prints:

int32_t hello = C_RegisterMessage("Hi, <<STR_PLAYERNAME>>!\nNice day for it.<<BTN>>");

An end code is added when the text doesn't finish with one. Questions with two to four answers, each leading to another message, come from C_RegisterQuestion; the ChoiceSelected event reports the answer.

Windows, macOS, LinuxYesSources are compiled at load time; a mod may also ship prebuilt binaries.

iOS, WebNot yetCode mods are skipped on these platforms for now.

On Windows a mod can only read or write a game variable whose declaration uses extern_s, which becomes __declspec(dllimport) when TinyCC builds a mod. The core globals (common_data, gamePT, graph_class, padmgr_class) already do; functions don't need it. Include port/api/cvar.h instead of libultraship's console variable bridge, whose colour types conflict with the game's. Unsigned mods load with a warning; archives can be signed with libultraship/tools/sign.py.

Listening to events

The game fires events at the points mods are likely to care about. A listener receives an IEvent* to cast to the event's own struct. All events fire on the game thread.

static ListenerID sSpawn;

static void OnActorSpawn(IEvent* event) {
    ActorSpawn* spawn = (ActorSpawn*)event;
    if (*spawn->profile == mAc_PROFILE_BEE) {
        event->Cancelled = true;   // no more bees
    }
}

MOD_INIT() {
    sSpawn = REGISTER_LISTENER(ActorSpawn, EVENT_PRIORITY_NORMAL, OnActorSpawn);
}
KindWhat a listener can do
cancellableSet event->Cancelled = true to stop the game's default behaviour. Each event says what cancelling does.
Pointer fieldsFields typed as pointers, like int32_t* msgNo, let a listener change what the game uses by writing through them, without cancelling.
polledDetected by comparing game state once per play frame: they fire on the frame after the change and never outside play.
LookupsEvents such as ItemLookup ask who owns a number. The content APIs answer them for you; mods rarely need to.

UNREGISTER_LISTENER(Event, id) removes a listener while the mod runs; listeners still registered when it unloads are removed for it. Game structs reach listeners as forward-declared tags (struct actor_s*, struct game_play_s*, …): include the matching game header, such as m_actor.h or m_play.h, to read them.
